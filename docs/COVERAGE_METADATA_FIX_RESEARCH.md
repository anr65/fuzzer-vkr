# Исследование передачи coverage metadata из target worker

Статус: core-фикс реализован и подтверждён регрессионными тестами и end-to-end пересборкой YAML coverage.

Дата: 16 августа 2026 года.

## 1. Практическая проблема

`CoverageRenderer` работает в родительском процессе и строит отчёт по `Fuzzer::$fileInfos`. После перехода к изолированному `TargetWorker` часть PHP-файлов стала загружаться лениво уже после `fork()` — внутри дочернего процесса.

Include interceptor инструментировал такие файлы корректно, и их block ID участвовали в runtime coverage features. Однако созданные `FileInfo` оставались только в copy-on-write памяти child. Родитель видел features, но не знал, какому файлу и позиции соответствуют их block ID. Поэтому HTML-отчёт часового YAML A/B содержал только 4/16 блоков файлов, загруженных до fork, несмотря на 12,4–12,6 тысячи накопленных features.

## 2. Гипотеза H5

> Если worker после выполнения передаёт родителю metadata новых инструментированных файлов, а родитель сохраняет её для `CoverageRenderer`, HTML-отчёт начинает включать лениво загруженный vendor-код. При этом block ID должны оставаться стабильными после автоматического restart worker.

Простой перенос только `FileInfo` недостаточен. После смерти worker новый child создаётся из состояния родителя. Если родитель лишь увеличит счётчик block ID, тот же лениво загружаемый файл при повторной инструментации получит другие ID. Старые corpus features и новые выполнения станут описывать разные идентификаторы одного блока.

## 3. Реализованное решение

### 3.1. Данные, возвращаемые worker

`TargetExecutionResult` теперь может содержать дельту `instrumentedFiles`. Для каждого нового файла передаются:

- SHA-256 исходного кода;
- инструментированный PHP-код;
- карта `blockIndex => source position`.

Worker запоминает сигнатуры metadata, существовавшей на момент fork, и отправляет только новые или изменившиеся записи. Поэтому полный кэш не передаётся после каждого input.

### 3.2. Слияние в родительском процессе

Родитель:

1. проверяет структуру metadata;
2. отклоняет конфликтующие описания одного пути;
3. восстанавливает `FileInfo` для `CoverageRenderer`;
4. сохраняет инструментированный код в `instrumentedFileCache`;
5. резервирует полученный диапазон block ID в родительском `Instrumentor`.

Metadata сливается до преобразования edge counts в coverage features.

### 3.3. Стабильность после restart

Новый worker наследует родительский `instrumentedFileCache`. Когда он снова загружает известный lazy-файл, interceptor проверяет SHA-256 исходника и возвращает сохранённый инструментированный код вместо новой инструментации. Следовательно, файл использует те же block ID, что и до restart.

Если содержимое файла изменилось либо worker прислал несовместимую карту, выполнение завершается явной ошибкой вместо скрытого смешивания coverage namespaces.

## 4. Изменённые компоненты

- `src/TargetExecutionResult.php` — поле для instrumentation metadata;
- `src/TargetWorker.php` — дельта metadata в IPC-ответе;
- `src/Fuzzer.php` — кэш инструментированного кода, слияние `FileInfo`, повторное использование после restart;
- `src/Instrumentation/Context.php` — резервирование диапазона block ID;
- `src/Instrumentation/Instrumentor.php` — публичная передача резервирования в context;
- `test/Experiment/TargetWorkerTest.php` — проверка дельта-протокола;
- `test/Experiment/CoverageMetadataTest.php` — lazy include и стабильность features после принудительного worker timeout/restart;
- `test/fixtures/coverage_metadata_*.php` — изолированная динамически загружаемая цель.

## 5. Подтверждённые инварианты

Регрессионные тесты подтверждают:

1. lazy-файл, появившийся только внутри child, передаётся родителю;
2. одна и та же metadata не отправляется повторно при каждом input;
3. `Fuzzer::$fileInfos` после выполнения содержит lazy-файл;
4. после timeout, уничтожения child и создания нового worker набор coverage features одинакового input не меняется;
5. карта `blockIndexToPos` lazy-файла до и после restart идентична.

Также пройдены существующие тесты инструментации и core-фикса корпуса. PHPStan для изменённых core-файлов завершился без ошибок при лимите 512 МБ.

## 6. Ограничения и ожидаемая цена

- Родитель теперь удерживает инструментированный код lazy-файлов. Это осознанная плата за стабильность block ID между worker generations и должно быть измерено отдельно по parent RSS.
- Metadata, созданная во время worker timeout до его принудительного уничтожения, теряется вместе с edge counts этого незавершённого input. Следующий успешный запуск проинструментирует файл заново в свободном диапазоне ID.
- IPC timeout сейчас ограничивает ожидание начала ответа, но не время чтения уже начавшегося большого frame. При очень большом первом metadata delta это может потребовать отдельного ограничения размера/времени.
- Корректность HTML coverage на Symfony YAML пока подтверждена структурным тестом, но не повторной end-to-end генерацией отчёта.

## 7. Результат end-to-end проверки

Пользователь пересобрал coverage по сохранённому корпусу fixed-варианта часового эксперимента `yaml-memory-leak-hour-r01`. Новый отчёт создан в `fixed/coverage-metadata-fixed`.

Проверка артефактов показала:

- контейнер завершился, незавершённого процесса генерации отчёта нет;
- создано 12 HTML-файлов, включая index;
- index содержит 11 ссылок, отсутствующих или пустых страниц нет;
- отображаются девять файлов `vendor/symfony/yaml/...`;
- суммарное покрытие отчёта: 817/1054 блоков, или 77,51%;
- непосредственно Symfony YAML: 813/1038 блоков, или 78,32%;
- прежний неполный отчёт содержал только 4/16 блоков.

Таким образом, корневая причина подтверждена: runtime coverage собирался и до исправления, но metadata лениво загруженных после fork файлов не попадала в родительский renderer. Core-фикс восстанавливает соответствие между coverage features, исходными файлами и позициями блоков.

Открытым остаётся отдельное измерение дополнительного parent RSS, создаваемого кэшем инструментированного кода. Оно не влияет на доказательство корректности metadata, но должно учитываться при следующем длительном memory A/B.
