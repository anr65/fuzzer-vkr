# Исследование core-утечки памяти корпуса nikic/PHP-Fuzzer

Статус: дефект и его memory-механизм подтверждены; часовой YAML A/B показал снижение peak parent RSS на 31,8% и большее число features, однако достижение baseline лимита памяти и причинный прирост полного code coverage пока не доказаны.
Дата эксперимента: 16 августа 2026 года.

## 1. Исследовательская проблема

В исходной реализации `Corpus::addEntry()` один и тот же вход мог многократно приниматься как интересный, если очередное выполнение показывало новые признаки покрытия. Запись в `entriesByHash` при этом заменялась, но новый объект безусловно добавлялся в `entriesByIndex`. Старые объекты оставались достижимыми и не освобождались. Дополнительно каждый объект сохранял полную PHP-карту `features` своего выполнения.

В результате логический размер корпуса мог оставаться равным одному seed, тогда как физическое число объектов, заявленный размер входных данных и потребление памяти росли после каждого принятия.

## 2. Гипотеза H4

**H4 — обеспечение уникальности входов и компактного хранения покрытия в ядре корпуса устраняет неограниченный рост памяти и позволяет продолжить накопление покрытия при том же лимите RAM.**

Формальная причинная цепочка:

1. одинаковый seed повторно наблюдается с новым feature;
2. baseline заменяет значение в `entriesByHash`, но добавляет ещё один объект в `entriesByIndex`;
3. каждый оставшийся объект удерживает полную карту features;
4. память растёт примерно пропорционально числу повторных принятий;
5. процесс достигает лимита памяти и больше не может исследовать новые состояния программы.

Ожидаемое действие исправления:

1. один набор входных байтов представлен одной записью корпуса;
2. новые features повторного наблюдения передаются существующей записи;
3. полная карта выполнения освобождается после принятия кандидата;
4. в долгоживущей записи остаются вход и только принадлежащие ему уникальные features;
5. при том же лимите памяти фаззер способен обработать больше наблюдений и сохранить больше признаков покрытия.

### Нулевая гипотеза H0

Исправление не устраняет рост памяти либо достигает этого ценой потери features. При одинаковом потоке наблюдений fixed-версия должна исчерпать память примерно в той же точке, показать сопоставимый рост памяти или сохранить меньше признаков покрытия.

## 3. Критерии принципиальной практической значимости

Гипотеза считается подтверждённой на уровне механизма, если одновременно выполняются условия:

- на равном бюджете наблюдений fixed сохраняет столько же features, сколько baseline;
- `entriesByHash` и `entriesByIndex` fixed-версии остаются согласованными;
- прирост памяти fixed как минимум в 10 раз меньше baseline;
- под одинаковым жёстким лимитом памяти baseline не завершает заданный бюджет, а fixed завершает его и продолжает накапливать features.

Последнее условие важно для практической интерпретации: исправление должно не просто уменьшать число мегабайт, а устранять причину преждевременной остановки coverage-guided поиска.

## 4. Исправление

Изменения внесены непосредственно в ядро корпуса:

- `Corpus::addEntry()` теперь возвращает признак физического добавления новой записи;
- при совпадении хеша новый объект не добавляется в `entriesByIndex`;
- новые `uniqueFeatures` повторного наблюдения объединяются с существующей записью и глобальным `seenFeatures`;
- `totalLen` не увеличивается для повторного входа;
- после физического добавления или замены записи полная `features` очищается;
- вызывающий код не создаёт повторный файл и не регистрирует повторный seed в scheduler;
- для повторного входа в журнале используется действие `MERGE`, а не `NEW`.

Изменённые файлы:

- `src/Corpus.php`;
- `src/CorpusEntry.php`;
- `src/Fuzzer.php`.

Добавлены:

- `test/CorpusTest.php` — регрессионные тесты инвариантов корпуса;
- `scripts/benchmark_corpus_memory_fix.php` — воспроизводимый парный memory benchmark.

## 5. Дизайн первичного эксперимента

### 5.1. Seed

В обеих группах использовался один и тот же реальный seed из зафиксированного YAML-корпуса:

```text
corpora/yaml-v1/seeds/B04_depth_width.yaml
SHA-256: b96bb2ea3b9b7c8d2116f96bb24bf51ba3c0ea4b65e142bd0dc1bf3546a61f66
Размер: 121 байт
```

### 5.2. Модель наблюдений покрытия

Один и тот же seed подаётся многократно. Каждое наблюдение содержит:

- 2000 общих features;
- один новый feature, уникальный для текущего наблюдения.

Этот сценарий изолирует найденный дефект: одинаковые входные байты повторно признаются интересными из-за новых features, что возможно на stateful или недетерминированной цели.

Эксперимент не имитирует мутации и не сравнивает эффективность поиска путей. Он проверяет конкретный причинный механизм между повторным принятием seed, структурой корпуса, сохранностью coverage-сигнала и исчерпанием памяти.

### 5.3. Сравниваемые варианты

**Baseline:** локальная копия прежней логики `addEntry()` внутри benchmark-скрипта: замена записи по хешу, безусловное добавление в индекс, сохранение полной карты features.

**Fixed:** фактическая исправленная реализация класса `PhpFuzzer\Corpus`.

Варианты запускаются отдельными PHP-процессами, чтобы память одного измерения не влияла на другое.

### 5.4. Среда и управление переменными

```text
PHP: 8.4.18
memory_limit: 128M
seed: одинаковый
порядок features: одинаковый
features на выполнение: 2001
```

Команды равного бюджета:

```bash
php -d memory_limit=128M scripts/benchmark_corpus_memory_fix.php baseline 1500 2000
php -d memory_limit=128M scripts/benchmark_corpus_memory_fix.php fixed    1500 2000
```

Команды проверки достижения предела:

```bash
php -d memory_limit=128M scripts/benchmark_corpus_memory_fix.php baseline 5000 2000
php -d memory_limit=128M scripts/benchmark_corpus_memory_fix.php fixed    5000 2000
```

## 6. Результаты

### 6.1. Равный бюджет: 1500 наблюдений

| Метрика | Baseline | Fixed |
|---|---:|---:|
| Статус | completed | completed |
| Завершено наблюдений | 1500 | 1500 |
| Сохранено features | 3500 | 3500 |
| `entriesByHash` | 1 | 1 |
| `entriesByIndex` | 1500 | 1 |
| Заявленный объём входов | 181 500 байт | 121 байт |
| Текущая используемая память | 125 843 104 байт | 2 099 296 байт |
| Прирост используемой памяти | 124 162 736 байт | 418 936 байт |
| Выделенная PHP память | 130 023 424 байт | 4 194 304 байт |

Обе версии сохранили одинаковые 3500 features. При этом прирост используемой памяти baseline оказался приблизительно в **296 раз** больше, чем у fixed. По текущему абсолютному потреблению fixed использовал приблизительно в **60 раз** меньше памяти.

Следовательно, снижение памяти не достигнуто отбрасыванием coverage-информации.

### 6.2. Практический предел: план 5000 наблюдений при 128 МБ

| Метрика | Baseline | Fixed |
|---|---:|---:|
| Статус | memory_exhausted | completed |
| Завершено из 5000 | 1570 | 5000 |
| Доля выполненного бюджета | 31,4% | 100% |
| Сохранено features к моменту завершения | 3570 | 7000 |
| `entriesByHash` | 1 | 1 |
| `entriesByIndex` | 1570 | 1 |
| Заявленный объём входов | 189 970 байт | 121 байт |
| Текущая используемая память | 131 648 400 байт | 2 426 976 байт |
| Прирост используемой памяти | 129 968 032 байт | 746 616 байт |
| Пиковая выделенная память | 134 217 728 байт | 4 194 304 байт |

Baseline аварийно остановился при попытке выделить память для 1571-го повторного объекта. Fixed выполнил весь бюджет и сохранил все 7000 наблюдавшихся features. К концу fixed-эксперимента прирост используемой памяти составлял менее 1 МБ.

При одном логическом seed fixed обработал минимум в **3,18 раза** больше наблюдений, чем baseline успел обработать до OOM. Это нижняя граница эффекта: fixed завершил заданный бюджет, поэтому его фактический предел данным опытом не найден.

## 7. Проверка корректности

Добавлены два регрессионных теста:

1. повторный вход с новым feature объединяет coverage, но не увеличивает корпус, индекс и `totalLen`;
2. замена входа при минимизации сохраняет ownership уникальных features и не оставляет полную карту выполнения.

Результат полного тестового набора:

```text
PHPUnit 9.6.34
35 / 35 tests passed
6192 assertions
Memory: 10.00 MB
```

Статический анализ нового benchmark-кода не выявил ошибок после исправления его локального предупреждения. Полный запуск PHPStan по рабочему дереву всё ещё сообщает ранее существовавшие замечания в конфигурации подавлений, `TargetWorkerTest.php` и `MutatorTest.php`; они не относятся к данному исправлению.

## 8. Вывод по H4

Первичная гипотеза **подтверждена на уровне причинного механизма**.

Эксперимент показал одновременно:

- сохранность того же coverage-сигнала при равном числе наблюдений;
- устранение расхождения между логическим корпусом и индексом выборки;
- снижение прироста памяти приблизительно в 296 раз на равном бюджете;
- устранение OOM в сценарии, где baseline выполняет только 31,4% заданного бюджета;
- возможность продолжить накопление features после точки обязательной остановки baseline.

Практическая значимость состоит не в более аккуратном завершении процесса, а в устранении внутренней причины, которая ограничивает продолжительность фаззинга и достижимое покрытие при фиксированном объёме RAM.

## 9. Границы доказательства

Данный опыт является контролируемым microbenchmark ядра корпуса. Он доказывает наличие дефекта, его причинную связь с OOM и сохранность features после исправления. Он ещё не доказывает конкретный прирост строкового или веточного покрытия на реальном приложении, потому что поток features в опыте задан детерминированно.

Для окончательного эмпирического подтверждения в ВКР требуется второй этап:

1. выбрать одну цель, на которой ранее воспроизводился рост памяти;
2. зафиксировать исходный corpus, PRNG seed, Docker image и лимит RAM;
3. выполнить baseline и fixed без supervisor-перезапусков;
4. сравнить peak RSS, наклон роста памяти, число выполнений до остановки, время до остановки, features и фактическое code coverage;
5. повторить опыт на нескольких PRNG seeds для оценки воспроизводимости эффекта.

До выполнения второго этапа корректная формулировка результата: **core-фикс принципиально снимает memory-bound ограничение продолжительности фаззинга; величина прироста покрытия на конкретной реальной цели подлежит отдельному измерению**.

## 10. Первый end-to-end пилот на `request_mix_3`

После подтверждения механизма выполнен первый парный запуск полного фаззера:

```text
experiment_id: memory-leak-e2e-20260816-r01
target: request_mix_3/target.php
seed: B04_depth_width.yaml, 121 байт
PRNG seed: 735457
лимит heap: 128 МБ
длительность варианта: 90 секунд
supervisor-перезапуски: отключены
порядок: baseline, затем fixed
```

### 10.1. Результаты пилота

| Метрика | Baseline | Fixed |
|---|---:|---:|
| Статус | completed | completed |
| Executions | 67 815 | 70 997 |
| Unique features | 4186 | 4187 |
| Логический corpus | 20 | 18 |
| События `NEW` | 22 | 17 |
| События `MERGE` | отсутствует в baseline | 4 |
| События `REDUCE` | 156 | 107 |
| Peak parent RSS | 44 928 КБ | 44 224 КБ |
| Peak worker RSS | 65 312 КБ | 70 480 КБ |
| Peak суммарный RSS | 98 480 КБ | 105 664 КБ |
| HTML coverage | 648/2437 | 648/2437 |

Артефакты запуска находятся в `corpora/runs/memory-leak-e2e-20260816-r01`.

### 10.2. Интерпретация

Этот пилот **не подтверждает и не опровергает практический эффект H4 на реальной цели**, потому что дефект не был достаточно активирован:

- оба варианта штатно завершили 90-секундный бюджет;
- baseline не достиг лимита памяти;
- разница peak parent RSS составила менее 1 МБ;
- фактическое покрытие получилось одинаковым;
- в обоих вариантах происходили очень частые минимизации корпуса.

Ключевая причина недостаточной чувствительности — выбранный seed длиной 121 байт. За 90 секунд baseline выполнил 156 операций `REDUCE`. Текущая реализация `replaceEntry()` при каждой редукции пересобирает `entriesByIndex` из `entriesByHash`. Эта операция побочно удаляет ранее накопленные дубли и не позволяет утечке долго развиваться.

Таким образом, пилот выявил важный модератор эффекта: рост памяти наиболее опасен после достижения минимальной длины входов или на фазах без частых редукций. Первый запуск нельзя использовать как доказательство отсутствия проблемы.

Дополнительно суммарный RSS в основном определялся worker-процессом Laravel. Core-утечка корпуса находится в родительском процессе, поэтому основной метрикой исправления должен быть именно `parent_rss_kb`, а worker RSS необходимо показывать отдельно как контрольную метрику.

## 11. Уточнённый end-to-end эксперимент

Для второго запуска подготовлен минимальный seed `corpora/memory-leak-ab-v1/minimal_a.txt`. После достижения длины 1 дальнейшая минимизация невозможна, поэтому `replaceEntry()` перестаёт периодически очищать индекс. Это делает опыт чувствительным именно к повторному принятию одинаковых коротких входов.

Рекомендуемый запуск:

```bash
SEED_SOURCE="$PWD/corpora/memory-leak-ab-v1/minimal_a.txt" \
DURATION_SECONDS=300 \
MEMORY_LIMIT_MB=128 \
PRNG_SEED=735457 \
scripts/run_memory_leak_end_to_end.sh memory-leak-e2e-minimal-r01
```

Runner последовательно выполнит baseline и fixed без supervisor-перезапусков, сохранит exit code, stdout/stderr, журнал фаззера, stability CSV, посекундный RSS родителя и worker, corpus каждого варианта и HTML coverage.

### 11.1. Основной критерий

Практический эффект считается подтверждённым, если baseline достигает soft memory limit и завершается с exit code 42, а fixed:

- проходит точку остановки baseline;
- выполняет полный временной бюджет;
- сохраняет bounded parent RSS;
- после точки остановки baseline обнаруживает дополнительные features или покрытые блоки.

Если baseline снова не достигает лимита, сравниваются наклоны `parent_rss_kb` во второй половине запуска. Положительный ненулевой наклон baseline при близком к нулю наклоне fixed подтверждает эффект памяти, но для утверждения о дополнительном покрытии потребуется более длительный бюджет.

### 11.2. Ограничение сравнения покрытия

`request_mix_3` использует `random_int()` внутри target, поэтому одинаковый PRNG seed фаззера не делает target полностью детерминированным. Один pair подходит для воспроизведения memory-bound поведения, но различие итогового покрытия нельзя целиком приписывать исправлению.

Для итоговой оценки покрытия после воспроизведения OOM нужны либо несколько парных повторов, либо детерминированная версия request-target. До этого момента корректно разделять два вывода:

- причинное влияние core-фикса на память уже подтверждено microbenchmark;
- влияние на реальное code coverage требует воспроизводимого end-to-end подтверждения.

## 12. Метрики итогового эксперимента

Рекомендуемая основная метрика — покрытие, достигнутое до первого исчерпания 128 МБ без перезапуска. Дополнительные метрики:

- максимальный RSS родительского процесса и worker;
- байты прироста памяти на 1000 событий `NEW`/`MERGE`;
- `count(entriesByIndex) / count(entriesByHash)`;
- executions и elapsed time до OOM;
- число features и покрытых строк в момент остановки baseline;
- дополнительное покрытие fixed после этой точки.

Если fixed при равных условиях проходит точку OOM baseline и после неё открывает воспроизводимые новые строки или ветви, практическая значимость для coverage-guided fuzzing будет подтверждена уже end-to-end.

### 13.2. Проверка основного критерия

Заранее определённый критерий практической значимости **не выполнен**:

- baseline не достиг soft memory limit 128 МБ;
- baseline не завершился с exit code 42;
- fixed не показал меньший peak parent RSS;
- fixed не продолжал работу после точки OOM baseline, потому что такой точки не было;
- разница в один покрытый блок находится внутри неопределённости недетерминированной цели.

Следовательно, этот запуск нельзя использовать как доказательство того, что core-фикс повышает реальное покрытие `request_mix_3`.

### 13.3. Почему минимальный seed не изолировал дефект полностью

Минимальная длина только исходного seed не запрещает фаззеру создавать более длинные интересные входы. В ходе запуска максимальная длина corpus entries выросла до 140 байт в baseline и до 98 байт в fixed. После этого снова стали возможны минимизации:

- baseline выполнил 72 `REDUCE`;
- fixed выполнил 42 `REDUCE`.

Каждый `replaceEntry()` пересобирает `entriesByIndex` из `entriesByHash`, поэтому накопленные baseline-дубликаты периодически удалялись. Тем не менее дефект проявился функционально: оценочно 10 событий `NEW` baseline не увеличили логический corpus, тогда как fixed зарегистрировал 15 явных событий `MERGE` и не создавал для них новые записи.

### 13.4. Обнаруженная доминирующая проблема worker

Хотя supervisor был отключён, target worker автоматически перезапускался после внутренних падений:

- baseline сменил worker PID один раз примерно на 150-й секунде;
- fixed сменил worker PID примерно на 139-й и 274-й секундах;
- stderr содержит `Allowed memory size of 268435456 bytes exhausted`;
- аварии происходили в процессе загрузки и инструментирования Laravel-классов через include interceptor;
- родительский фаззер не завершался: `TargetWorker` обнаруживал умерший child и создавал новый при следующем выполнении.

Это означает, что формально «один 300-секундный запуск» фактически состоял из нескольких worker-сессий. Перезапуск сбрасывал память и target state. После смены worker PID наблюдались новые bursts покрытия, поэтому итоговые features смешивают работу нескольких target-процессов.

Soft limit `--memory-limit=128` проверяет только `memory_get_usage(true)` родительского фаззера. Он не контролирует child worker, у которого действовал PHP `memory_limit=256M`. Поэтому текущая метрика способна сообщить штатное завершение фаззера даже после неоднократных target-side OOM.

### 13.5. Итоговая интерпретация

По совокупности двух end-to-end пилотов:

1. Исправление действительно поддерживает инвариант корпуса: повторное покрытие одного входа оформляется как `MERGE`, а не как физически новая запись.
2. В контролируемом microbenchmark это устраняет неограниченный рост памяти.
3. На `request_mix_3` за 90 и 300 секунд накопление дубликатов регулярно прерывалось операциями `REDUCE`, поэтому не стало memory-bound фактором.
4. Практический прирост реального покрытия от исправления на этой цели не доказан.
5. Фактическим memory-bound ограничением `request_mix_3` оказался долгоживущий worker Laravel, достигающий 256 МБ и неявно перезапускаемый.

Для ВКР core-фикс корпуса можно описывать как исправление корректности и потенциальной неограниченной утечки, подтверждённое unit/memory regression. Утверждение, что именно он обеспечивает существенно большее покрытие реального Laravel target, текущими данными делать нельзя.

## 14. Следующее направление исследования

Следующей основной гипотезой целесообразно сделать управление памятью target worker, потому что именно его OOM реально разрывает непрерывный процесс исследования программы.

До изменения поведения нужно добавить наблюдаемость child-процесса:

- возвращать из worker после каждого выполнения `memory_get_usage(false)` и `memory_get_usage(true)`;
- регистрировать PID и номер worker generation;
- явно логировать причину смерти и момент автоматического создания нового worker;
- отделять coverage, найденное до и после каждого worker restart;
- проверять, растёт ли live memory при повторении одного входа или только allocator RSS;
- измерять число загруженных классов/файлов и размер instrumentation state.

После локализации источника можно сравнивать полноценное исправление с baseline. Периодический restart по RSS допустим только как защитный контрольный вариант, но не как основное решение исследовательской гипотезы.

## 15. Часовой эксперимент на детерминированной YAML-цели

Для следующей проверки выбран `targets/yaml_target.php` и продолжительность 3600 секунд на каждый вариант. В отличие от `request_mix_3`, YAML-target использует `DeterministicYamlParser` и не вызывает `random_int()`. Это устраняет главный источник неопределённости предыдущих пилотов.

### 15.1. Что именно проверяет YAML-эксперимент

На детерминированной цели одинаковый вход не должен внезапно показывать новые features. Поэтому ветвь объединения повторного входа (`MERGE`) может вообще не активироваться. Часовой YAML-запуск в первую очередь проверяет вторую часть core-фикса: отказ от хранения полной карты `features` в каждой долгоживущей записи корпуса.

Проверяемая подгипотеза:

> При одинаковой детерминированной траектории фаззинга baseline удерживает полную feature-map каждого corpus entry, поэтому parent memory растёт быстрее; fixed хранит только unique-feature ownership и показывает меньший peak RSS и меньший наклон памяти без потери покрытия.

Ожидается, что до возможной остановки baseline варианты будут иметь одинаковые либо практически идентичные:

- mutation sequence при PRNG seed 735457;
- число unique features на общем execution-budget;
- состав corpus;
- HTML coverage.

Различаться должны главным образом parent RSS и, возможно, скорость выполнения из-за давления на память.

### 15.2. Зафиксированная конфигурация

```text
target: targets/yaml_target.php
seed: corpora/yaml-v1/seeds/B04_depth_width.yaml
PRNG seed: 735457
duration: 3600 секунд на baseline + 3600 секунд на fixed
soft parent memory limit: 128 МБ
target timeout: 3 секунды
stability interval: 1000 executions
supervisor restart: выключен
yaml-cache: выключен
variant order: baseline, затем fixed
```

Запуск:

```bash
scripts/run_yaml_memory_leak_hour.sh yaml-memory-leak-hour-r01
```

Рекомендуемый запуск в Docker:

```bash
docker build \
  --build-arg VCS_REF="$(git rev-parse HEAD)" \
  --build-arg VCS_DIRTY="$(test -z "$(git status --porcelain)" && echo false || echo true)" \
  -t fuzzer-vkr:yaml-memory-leak .

docker run --rm \
  --name yaml-memory-leak-hour-r01 \
  --memory=512m \
  --cpus=2 \
  -v "$PWD/corpora/runs:/app/corpora/runs" \
  --entrypoint bash \
  fuzzer-vkr:yaml-memory-leak \
  scripts/run_yaml_memory_leak_hour.sh yaml-memory-leak-hour-r01
```

Лимит контейнера 512 МБ намеренно выше soft limit родительского фаззера 128 МБ и PHP worker limit 256 МБ. Это позволяет зафиксировать внутреннюю причину остановки в логах вместо принудительного уничтожения всего контейнера Docker runtime.

Суммарная ожидаемая длительность — немного более двух часов, потому что baseline и fixed выполняются последовательно, после каждого варианта строится HTML coverage.

### 15.3. Критерии оценки

Основные метрики:

- peak и временной ряд `parent_rss_kb`;
- наклон parent RSS на общем интервале executions и во второй половине часа;
- exit code 42 и execution/time точки soft OOM, если он произойдёт;
- executions, unique features и corpus size;
- coverage blocks из `coverage/index.html`;
- число и время смен worker PID;
- события `NEW`, `MERGE`, `REDUCE`.

Практическая значимость подтверждается, если выполняется хотя бы один сильный критерий:

1. baseline достигает 128 МБ и останавливается, а fixed завершает час и после точки остановки baseline находит новые features/blocks;
2. оба завершают час, но fixed при сопоставимом покрытии показывает устойчиво меньший parent RSS и существенно меньший положительный наклон памяти.

Если память и покрытие практически совпадут, это будет означать, что на детерминированном YAML target обе исправленные структуры не являются значимым ограничителем в часовом масштабе. Такой отрицательный результат также должен быть сохранён без изменения критериев после просмотра данных.

## 16. Результаты часового YAML A/B

Эксперимент `yaml-memory-leak-hour-r01` завершён. Оба варианта штатно отработали заданный час, остановились по time limit и вернули exit code 0. Stderr пуст, построение HTML-отчёта завершилось с кодом 0. Артефакты запуска сохранены в `corpora/runs/yaml-memory-leak-hour-r01`.

| Метрика за час | Baseline | Fixed | Изменение fixed |
|---|---:|---:|---:|
| Executions | 7 026 066 | 6 613 987 | −412 079 (−5,87%) |
| Unique features | 12 385 | 12 595 | +210 (+1,70%) |

Ключевой результат состоит не в том, что fixed сформировал меньший корпус. Напротив, в fixed логических entries и байтов на диске больше, но parent RSS меньше почти на треть. Это согласуется с заявленным механизмом исправления: долгоживущие записи перестали удерживать полную feature-map, а повторно принятые входы объединяются без создания физического дубликата.

Ветвь `MERGE` действительно активировалась 139 раз. Baseline не имеет отдельного действия `MERGE`, поэтому прямое сопоставление количества его дубликатов по журналу невозможно.

### 16.2. Сравнение при одинаковом execution-budget

Fixed выполнил меньше итераций за тот же час, поэтому финальное сравнение features само по себе смешивает эффективность поиска и скорость выполнения. На общем бюджете 6 613 987 executions получено:

| Метрика | Baseline, интерполяция | Fixed | Разница fixed |
|---|---:|---:|---:|
| Unique features | 12 344,8 | 12 595 | +250,2 (+2,03%) |
| Время достижения бюджета | 3382,6 с | 3600,6 с | +218,0 с (+6,45%) |

Таким образом, fixed сохранил примерно на 2,0% больше features на равном числе выполнений, но достиг этого execution-budget медленнее. Среднее число накопленных features по общей оси executions выросло только на 0,70%, поэтому результат следует считать умеренным, а не многократным ростом эффективности.

Пороговые точки подтверждают более раннее накопление поздних features:

| Порог | Baseline | Fixed | Изменение fixed |
|---|---:|---:|---:|
| 12 000 features, время | 2122,88 с | 1890,86 с | −232,02 с (−10,93%) |
| 12 000 features, executions | 4 423 088 | 3 916 317 | −506 771 (−11,46%) |

Среднее число features по времени составило 10 993,9 в baseline и 11 121,7 в fixed: +1,16% в пользу исправления.

| Время | Baseline | Fixed | Экономия fixed |
|---:|---:|---:|---:|
| 10 с | 49 024 КБ | 40 896 КБ | 8128 КБ |
| 600 с | 69 516 КБ | 47 052 КБ | 22 464 КБ |

Линейный наклон RSS нельзя использовать как единственное доказательство: PHP allocator выделяет память ступенями, и момент очередной ступени существенно меняет slope на выбранном интервале. Для этого запуска надёжнее сравнивать peak/end parent RSS и синхронные точки времени. Снижение worker и total RSS также нельзя полностью приписывать фиксу корпуса, потому что варианты прошли разное число worker generations.

### 16.4. Что подтверждено

1. Core-фикс имеет практический memory-эффект в реальной часовой YAML-кампании: peak parent RSS уменьшился на 31,8%, хотя fixed сохранил больший логический и дисковый корпус.
2. Экономия памяти не достигнута ценой потери coverage features: fixed завершил час с +1,7% features и имеет +2,0% на общем execution-budget.
3. Исправленная ветвь объединения не является мёртвым кодом: зафиксировано 139 событий `MERGE`.
4. Фикс снижает ресурсную стоимость долгоживущего состояния фаззера и тем самым увеличивает запас до memory limit.

Это позволяет формулировать практическую значимость как **снижение memory pressure без потери feature-guided прогресса**. Более сильная формулировка «без фикса процесс останавливается и не достигает покрытия, которое достигается с фиксом» этим запуском не подтверждена: baseline не достиг soft limit 128 МБ.

### 16.5. Ограничение текущего измерения code coverage

Одинаковый HTML-результат 4/16 блоков не отражает фактическое покрытие Symfony YAML. `CoverageRenderer` родительского процесса знает только о файлах, загруженных до `fork()`. Классы Symfony YAML загружаются лениво внутри child worker; созданные там `FileInfo` остаются в copy-on-write памяти дочернего процесса и не передаются обратно родителю. Поэтому 12,4–12,6 тысячи runtime features нельзя корректно перевести в полный процент покрытия vendor-кода текущим HTML renderer.

Это отдельная проблема ядра инфраструктуры фаззера, мешающая оценивать достигнутое покрытие:

> Метаданные инструментированных после fork файлов и блоков должны передаваться из `TargetWorker` в родительский процесс либо полный набор целевых файлов должен инструментироваться до fork.

До такого исправления в выводах нужно использовать термин `coverage features`, а не заявлять процент полного code coverage Symfony YAML.

### 16.6. Угрозы валидности

- Проведена одна парная реплика с одним PRNG seed.
- Порядок не был контрбалансирован: baseline всегда запускался раньше fixed.
- Fixed прошёл 70 поколений worker против 43 у baseline; это искажает worker RSS, total RSS и wall-clock throughput.
- Оба варианта остались ниже soft parent limit 128 МБ, поэтому предотвращение фактической OOM-остановки не наблюдалось.
- Разные траектории корпуса не позволяют считать разницу +210 features исключительно прямым следствием меньшего RSS.

Следовательно, часовой запуск является сильным пилотным подтверждением memory-эффекта, но не статистическим доказательством прироста полного code coverage.

### 16.7. Итог по гипотезе H4

Гипотеза разделяется на два уровня:

- **механизм и resource effect — подтверждены**: инвариант корпуса исправлен, microbenchmark устраняет неограниченный рост, а реальный YAML A/B показывает −31,8% peak parent RSS без потери features;
- **предотвращение остановки и дополнительное полное code coverage — пока не подтверждены**: baseline не исчерпал 128 МБ, а renderer не видит лениво загруженный vendor-код.

Для подтверждающего этапа нужны несколько PRNG seeds, обратный порядок fixed/baseline и конфигурация, в которой baseline воспроизводимо достигает parent memory limit. До сравнения процентов покрытия необходимо исправить передачу coverage metadata из worker.

Полный машинно-читаемый итог и компактный отчёт находятся в `benchmark-reports/yaml-memory-leak-hour-r01/`.
