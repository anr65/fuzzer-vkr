# Часовой YAML A/B: core-фикс памяти корпуса

## Техническое резюме

Часовой эксперимент `yaml-memory-leak-hour-r01` подтверждает практический ресурсный эффект исправления ядра корпуса: peak RSS родительского фаззера снизился с 90 004 до 61 396 КБ, то есть на 31,8%. При этом fixed сохранил больше записей корпуса и завершил запуск с 12 595 coverage features против 12 385 у baseline. На равном бюджете 6 613 987 executions преимущество fixed составляет около 250 features, или 2,0%.

Результат доказывает снижение memory pressure без потери feature-guided прогресса. Он пока не доказывает предотвращение OOM и достижение дополнительного полного code coverage: baseline не достиг лимита 128 МБ, а HTML renderer не получает метаданные Symfony YAML, лениво загруженные после fork в child worker.

## Практическая интерпретация

Fixed использовал меньше памяти не потому, что обработал или сохранил меньше данных. Его корпус оказался на 53 entries и 38 865 байт на диске больше, но parent RSS был на 28 608 КБ ниже. Наблюдение соответствует механизму core-фикса: `CorpusEntry` больше не удерживает полную карту features, а повторное принятие одинаковых байтов объединяется с существующей записью.

Практически это означает больший запас до лимита памяти и возможность дольше поддерживать coverage-guided кампанию в том же RAM-бюджете. В этой конкретной реплике запас не был исчерпан: baseline завершил час штатно, поэтому утверждать, что fixed уже предотвратил остановку, нельзя.

## Сравнение при равном числе выполнений

Финальные значения получены при разном числе executions. На общем бюджете 6 613 987 итераций baseline интерполированно имел 12 344,8 features, fixed — 12 595. Преимущество fixed равно 250,2 features (+2,03%), но на выполнение этого бюджета fixed потребовалось на 218,0 секунды больше (+6,45%).

Поздние пороги coverage features fixed достигал эффективнее:

| Порог | Baseline | Fixed | Выигрыш fixed |
|---|---:|---:|---:|
| 12 000 features | 2122,88 с; 4 423 088 exec | 1890,86 с; 3 916 317 exec | −10,93% времени; −11,46% exec |
| 12 300 features | 3159,07 с; 6 169 605 exec | 2767,79 с; 5 344 521 exec | −12,39% времени; −13,37% exec |

Это свидетельствует о более продуктивной траектории fixed в данной реплике, но не позволяет отделить влияние памяти от различий corpus trajectory и worker timeouts.

## Дизайн и целостность эксперимента

- Target: `/app/targets/yaml_target.php`, SHA-256 `b9ecce9b5b30767af03409992d1a0de5fc167533a0c174c832c80abdabf561b5`.
- Seed: `B04_depth_width.yaml`, SHA-256 `b96bb2ea3b9b7c8d2116f96bb24bf51ba3c0ea4b65e142bd0dc1bf3546a61f66`, 121 байт.
- PRNG seed: 735457.
- По 3600 секунд на вариант; порядок baseline, затем fixed.
- Soft parent memory limit: 128 МБ; target timeout: 3 секунды.
- Supervisor restarts отключены.
- Оба варианта остановились по time limit, exit code 0; coverage renderer exit code 0; stderr пуст.
- Сырые временные ряды: `corpora/runs/yaml-memory-leak-hour-r01/{baseline,fixed}/rss.csv` и `stability.csv`.

## Ограничения

1. Одна реплика и один PRNG seed не дают статистической оценки разброса.
2. Порядок вариантов не обращался, поэтому возможен order effect.
3. Fixed сменил worker PID 69 раз, baseline — 42; worker RSS и throughput имеют сильный confound.
4. Ни один вариант не достиг soft parent limit, поэтому сильный критерий «baseline остановился, fixed продолжил» не выполнен.
5. HTML coverage 4/16 является неполным: родительский renderer не знает о Symfony-файлах, загруженных child worker после fork. Значения 12 385 и 12 595 следует называть coverage features, а не процентом полного покрытия Symfony YAML.

## Вывод для ВКР

Корректная формулировка:

> Исправление структуры корпуса nikic/PHP-Fuzzer снизило peak memory родительского процесса на 31,8% в часовом YAML A/B, одновременно сохранив на 1,7% больше coverage features. Это подтверждает практическую значимость как уменьшение memory pressure без потери прогресса фаззинга. Предотвращение OOM и прирост полного code coverage требуют отдельного подтверждающего эксперимента.

Некорректно по текущим данным утверждать, что baseline достиг только определённого процента покрытия и остановился по памяти: этого в запуске не произошло, а полный vendor coverage текущим renderer не измерен.

## Следующий подтверждающий шаг

1. Исправить передачу `FileInfo`/block metadata из `TargetWorker` в родительский процесс или выполнить предварительную инструментацию целевых Symfony-файлов до fork.
2. Повторить A/B на нескольких PRNG seeds с чередованием порядка baseline/fixed.
3. Подобрать заранее зафиксированный RAM-бюджет или длительность, при которых baseline воспроизводимо достигает parent limit, не меняя критерии после просмотра результата.
4. Основным causal-показателем оставить parent RSS; worker RSS анализировать отдельно по поколениям.

Машинно-читаемые метрики находятся в `summary.json`, контрольные точки памяти — в `memory_timeline.csv`.
